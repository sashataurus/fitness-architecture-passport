# ADR-001: Модульный монолит для приложения домашних тренировок

## Контекст и проблема

Приложение предназначено для самостоятельных домашних тренировок. Основные сценарии: авторизация, каталог и фильтрация тренировок, просмотр упражнений/видео, персональный план, проведение тренировки, оценка техники, сохранение и синхронизация прогресса.

Предметная область разделена на пять bounded contexts: профиль пользователя; каталог тренировок; персональный план и прогресс; проведение тренировки и анализ техники; питание. Выделены агрегаты `Workout`, `PersonalPlan`, `TrainingSession`; взаимодействие после завершения занятия выполняется через доменное событие `WorkoutCompleted`.

## Рассматриваемые варианты

1. **Простой монолит без модульных границ.** Один backend и общая кодовая база, компоненты могут напрямую обращаться к внутренним данным друг друга.
2. **Модульный монолит (выбран).** Один deployable backend, но пять контекстов с явными интерфейсами/контрактами, запретом прямого доступа к внутренним таблицам и репозиториям соседних модулей. Межконтекстные реакции на события выполняются через внутренний Event Bus.
3. **Микросервисы.** Каждый бизнес-контекст — автономный сервис со своим хранилищем и независимым деплоем; взаимодействие через сеть и брокер сообщений.

## Критерии и trade-offs

Оценка качественная: `++` хорошо, `+` приемлемо, `−` хуже для данного контекста.

| Критерий | Простой монолит | Модульный монолит | Микросервисы |
|---|---:|---:|---:|
| Time-to-Market | ++ | + | − |
| Scalability | − (масштаб целиком) | −/+ (масштаб целиком, модули подготовлены к выделению) | ++ (точечно) |
| Reliability | − (сильная связность) | + (границы и локализация ошибок внутри модулей) | + (изоляция отказов, но сеть добавляет сбои) |
| Cost / TCO | ++ | + | − (инфраструктура и эксплуатация) |
| Maintainability | − | ++ | + (при зрелых командах и контрактах) |
| Транзакции | ++ (локальные ACID) | ++ (локальные ACID) | − (Saga/eventual consistency) |
| Эксплуатация | ++ | + | − (мониторинг, tracing, оркестрация) |

## Решение

Выбрать **модульный монолит** с одним backend deployment и PostgreSQL. Внутри backend выделить пять модулей по bounded contexts. Каждый модуль владеет своей моделью и таблицами/схемой; соседние модули обращаются только через публичные интерфейсы и идентификаторы, а не напрямую к репозиториям. Межконтекстные реакции на завершение тренировки выполняются через внутренний Event Bus.

Мобильный клиент реализует Offline-First: локальный кэш/БД хранит каталог и состояние незавершенной сессии; сетевые запросы не блокируют стартовый экран. Синхронизация выполняется отдельно, с тайм-аутами и повторными попытками.

## Последствия

### Положительные
- Быстрее разработать и развернуть учебный проект, чем набор микросервисов.
- Локальные ACID-транзакции упрощают сохранение сессии и прогресса.
- Контексты и контракты уменьшают coupling и позволяют проверять архитектурные границы.
- Можно выделять отдельный модуль в сервис при подтвержденной необходимости.
- Offline-First и изоляция сетевых ошибок улучшают устойчивость пользовательского сценария.

### Отрицательные / риски
- Backend масштабируется целиком, даже если нагрузка сосредоточена в одном контексте.
- Ошибка или исчерпание ресурсов процесса может затронуть несколько модулей.
- При нарушении границ модульный монолит постепенно превращается в обычный монолит.
- Event Bus внутри процесса не обеспечивает независимую доставку при аварии; для надежной публикации событий в будущем потребуется Outbox.
- Offline-синхронизация требует разрешения конфликтов и контроля версий данных.

## Меры снижения рисков
- Архитектурные тесты запрещают импорт внутренних классов соседних модулей и прямой доступ к их репозиториям.
- В API единые DTO, схемы фильтров и формат ошибок.
- `TrainingSession.complete()` идемпотентен: повторный запрос не удваивает прогресс.
- Сетевые вызовы имеют timeout/retry; ошибки API не блокируют локальный интерфейс.
- События и операции синхронизации логируются; при росте требований внедряется Outbox.

## Что заставит пересмотреть решение
- Независимое масштабирование отдельных контекстов становится необходимым.
- Команды должны выпускать контексты независимо.
- Нагрузка или требования доступности требуют изоляции отказов на уровне сервисов.
- Эксплуатационная зрелость (мониторинг, CI/CD, tracing, on-call) позволяет оправдать стоимость распределенной системы.
